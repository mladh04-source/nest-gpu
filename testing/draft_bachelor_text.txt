1. Introduction and Motivation

NESTML is a domain-specific language for describing spiking neuron models and synaptic plasticity rules. One important advantage of NESTML is that a model only has to be specified once and can then be translated automatically to different target platforms, such as the CPU-based simulator NEST or the GPU-based simulator NEST GPU. To decide how the model equations should be handled, NESTML uses the ODE-toolbox. If an analytical solution is available, closed-form update equations are generated. Otherwise, numerical integration methods are used.

The original goal of this thesis was to compare different solver implementations for ordinary differential equations in GPU code generated by NESTML. More specifically, the native numerical solver implementation in NEST GPU was supposed to be extended or replaced by approaches based on third-party libraries, especially Boost C++ and Thrust. These implementations were then meant to be validated and compared in single-neuron and network experiments. Another objective was to study whether fixed-step methods are better suited to GPU architectures than variable-step methods.

During the practical work, however, it turned out that directly modifying the existing numerical solver infrastructure in NEST GPU was more difficult than expected. In particular, the RK5/RK45-based implementation is strongly embedded in the internal neuron update workflow. Because of this, integrating alternative external solver libraries would have required more substantial structural changes than originally planned. For that reason, the focus of the work was adjusted. Instead of starting with a direct replacement of the existing RK infrastructure, the project first moved to a prototype-based approach using an analytically generated neuron model from NESTML.



2. Objectives and Methodological Reorientation

At the beginning of the thesis, the aim was to replace the native numerical solver implementation in NEST GPU with approaches based on third-party solver libraries and to evaluate these implementations in terms of correctness and performance.

As the implementation work progressed, it became clear that a direct replacement of the RK-based infrastructure would not be straightforward. The current implementation is not limited to the numerical integration step itself, but is also closely connected to internal mechanisms for initialization, state updates, and state management in NEST GPU. This means that replacing the solver would also affect surrounding parts of the code.

Because of this, a reduced and more practical intermediate step was chosen. The idea was to take a model already generated by NESTML and functioning in NEST GPU, and then study how an additional numerical solver path could be integrated into this existing structure. This does not yet amount to a full replacement of the native solver infrastructure, but it does make it possible to test whether such an extension is feasible in principle.

This difference is important for interpreting the present results. The work does not claim that the native RK45 infrastructure has already been replaced. Rather, it shows that an alternative numerical integration path can be added to generated NEST-GPU code and validated first on a simpler single-neuron example.



3. Choice of the Test Model

The model chosen for this work was the NESTML-generated model iaf_psc_exp_neuron. This model describes a leaky integrate-and-fire neuron with exponentially decaying synaptic currents. In the standard version generated by NESTML, the model uses an analytical solver, because the corresponding differential equations can be solved in closed form using propagators.

This model was selected for practical reasons. Its dynamics are comparatively simple and therefore easier to analyze, and at the same time it already comes with a working codebase generated by NESTML for NEST GPU. This makes it possible to modify the solver path in a controlled way without first having to solve unrelated implementation problems. The model is therefore a suitable starting point for a first comparison between an analytical and a numerical update path.

At the same time, this also sets a limit on the interpretation of the results. The model itself does not actually require a numerical solver. The numerical path introduced here is therefore not intended as an improvement over the analytical solution, but as a way to investigate the technical integration and validation of an alternative numerical approach within the generated GPU code.



4. Implementation of the Modified Solver Path

For the model iaf_psc_exp_neuron_nestml, an additional experimental solver path was introduced. This path can be activated or deactivated using the compile-time macro USE_ODEINT_THRUST. If the macro is set to 0, the original analytical solver remains active. If it is set to 1, the numerical solver path is used.

This setup allows both variants to remain available in the same model implementation. As a result, the analytical and numerical executions can be compared directly under the same model assumptions.

4.1 Retaining the Original Analytical Path

The analytical code generated by NESTML was kept unchanged. In analytical mode, the precomputed propagator coefficients are still used to update the state variables of the neuron directly at each simulation step. This includes the exponential decay of the synaptic currents as well as the propagator-based update of the membrane potential.

Keeping the original analytical path was important because it provides a direct reference against which the numerical path can be checked.

4.2 Additional Numerical Solver Path

In numerical mode, a separate solver object is created during initialization of the neuron model. This object has access to the neuron’s state and parameter arrays, but it does not take over ownership of them from NEST GPU. Memory management therefore remains in the existing infrastructure, while the new solver is only responsible for carrying out the integration step.

The solver was implemented in the files iaf_psc_exp_odeint_solver.h and iaf_psc_exp_odeint_solver.cu. Even though the file name suggests an Odeint-based implementation, the current prototype mainly uses a Thrust-based execution style inspired by Odeint. It does not yet contain a full integration of more advanced Boost.Odeint solver classes. The actual update step is carried out in parallel on the GPU for all neurons using thrust::for_each.

4.3 Numerical Integration Method

In the current prototype, the numerical integration is based on an explicit Euler method with fixed step size. The synaptic currents are integrated numerically according to their decay equations. The membrane potential is also updated numerically as long as the neuron is not in the refractory period. If the neuron is refractory, the membrane potential stays unchanged and only the refractory counter is reduced by the step size.

This implementation was intentionally kept simple. At this stage, the main goal was not to use the most sophisticated integration method, but to create a robust and understandable prototype that could be integrated into the generated GPU code.

4.4 Separation of Integration and Event Processing

A key part of the implementation is the separation between continuous state integration and discrete event processing. The numerical solver only computes the ODE integration for one simulation step. After that, a separate CUDA kernel called PostUpdate is executed.

This PostUpdate kernel has two tasks. First, it processes incoming spike events by adding the buffered excitatory and inhibitory inputs to the synaptic currents. Second, it checks whether the membrane potential has reached threshold. If the threshold is crossed and the neuron is no longer refractory, a spike is emitted, the membrane potential is reset, and the refractory time is set again.

This follows the general update principle used in NEST and NESTML: first the continuous dynamics are integrated, and only afterwards are discrete state changes such as spike emission and reset applied.


5. Experimental Setup for the Initial Validation

For the initial validation, a single-neuron experiment was carried out in NEST GPU. The analytical and numerical versions of the model were compiled in separate installations and executed independently on the Jülich cluster.

The simulation was performed with a temporal resolution of 0.1 ms. In both cases, a single iaf_psc_exp neuron was created. The neuron received a constant external current of I_e = 1500 pA. In addition, a spike generator with spike times at 10 ms and 400 ms was connected to the neuron. The excitatory connection had a weight of 100 and a delay of 1.0 ms.

To observe the neuron dynamics, the relative membrane potential V_m_rel was recorded over the full simulation time of 500 ms. The recorded data were exported to text files and plotted afterwards. Separate batch jobs were used for the analytical and numerical versions so that both implementations could be tested under comparable conditions.

6. Evaluation and Comparison Metric

To measure the agreement between the analytical and numerical solutions, the root mean square error (RMSE) of the recorded membrane potential traces was calculated. For this, both time series were first aligned to the same length and then evaluated using

[
\mathrm{RMSE} = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(V_m^{\text{num}}(i)-V_m^{\text{ref}}(i))^2}
]

In Python, this was implemented as:

rmse = np.sqrt(np.mean((np.array(V_m[:n]) - np.array(V_m1[:n]))**2))





7. Initial Results

The results of the single-neuron simulation show very close agreement between the analytical and numerical solver paths for the test case considered. In the overlaid traces, no visible difference in the membrane potential can be observed. Both variants show the same qualitative behavior, with repeated threshold crossings, resets, and renewed charging of the membrane potential.

The plots produced separately for the analytical and numerical runs also show the same characteristic response pattern. This suggests that the numerical solver path reproduces the basic neuron dynamics correctly for this test setup.

The calculated RMSE was 0 within numerical precision. In this single-neuron experiment, no measurable deviation between the analytical and numerical solutions was found.


8. Discussion

The results obtained so far show that it is possible to integrate an additional numerical solver path into a NEST-GPU neuron model generated by NESTML. A practical advantage of the current implementation is that the original analytical path was kept unchanged and can therefore be used directly as a reference for validation.

At the same time, the current implementation should still be seen as a prototype and not as a replacement of the existing solver infrastructure. What has been shown is that an alternative numerical integration scheme can be integrated into the generated model code and executed in parallel on the GPU without changing the overall update structure completely. The usual separation between continuous integration and discrete event handling could also be preserved.

However, the present results are still limited. So far, only one model has been considered, and this model already has an analytical solution. 9. Outlook

The next step is to extend the validation of the numerical solver path to a broader range of test cases. This includes parameter studies with different membrane capacitances, time constants, threshold values, and external input currents, as well as simulations with different spike input patterns.

The analysis should also be extended from a single neuron to networks with multiple neurons. Only then will it be possible to assess whether the agreement between the analytical and numerical versions still holds under more complex interactions and a higher degree of parallelism.

Another important task will be the evaluation of performance. In line with the original project goals, analytical, native numerical, and alternative solver implementations should be compared in larger network simulations in order to identify possible differences in runtime, scalability, and GPU utilization.

In the longer term, it will also be relevant to examine whether more advanced methods from third-party libraries can be integrated in a useful way beyond the fixed-step Euler approach used here. In particular, it would be interesting to compare fixed-step methods with adaptive variable-step methods in the context of GPU-based simulation.

10. Preliminary Conclusion

In summary, the work carried out so far shows that an alternative numerical solver path can be integrated, in prototype form, into a NEST-GPU neuron model generated by NESTML. Because the existing RK-based infrastructure is strongly coupled to internal update mechanisms, the project did not begin with a direct replacement of the native implementation. Instead, a more reduced and methodologically manageable approach was chosen using an analytically solvable test model.

The numerical path implemented in this work runs in parallel on the GPU using the existing state arrays and preserves the separation between ODE integration and event processing. The first single-neuron experiments show very close agreement with the analytical reference solution. This provides a solid starting point for the next stages of the project, including network experiments, broader validation, and performance benchmarking.
